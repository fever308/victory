# Linux and Proton

VIctory is a Windows program. On Linux you can run the host tests, cross-build
`victory.exe`, and run that exe under Wine/Proton, where D3D12 goes through
vkd3d-proton. None of this is official support, and the title is **not
playable** on Linux any more than on Windows (see the status in the README).

You supply your own files. Keep them, and everything built or derived from
them, outside the repository: see [asset-policy.md](asset-policy.md). Never
commit game data, built binaries or logs that contain title bytes.

Tests use synthetic data generated by the repository's own code (for
example `tests/fixtures/hle-probe`); they need no game files, and none are
accepted on GitHub.

## Development with Nix

The checkout includes an x86-64 Linux development shell for NixOS and other
Linux distributions with Nix installed. `flake.lock` pins Nixpkgs and
rust-overlay; Rust's version, components and Windows MSVC target come from
`rust-toolchain.toml`. The shell adds Rust source and rust-analyzer for editors,
Cargo, Clippy, rustfmt, a native C compiler, cargo-xwin, LLVM/LLD, DXC,
ShellCheck and nixfmt.

```sh
nix develop                         # requires nix-command and flakes enabled in Nix
# Or, with no experimental Nix features required:
nix-shell                           # uses the same flake.lock pins

cargo fmt --all -- --check
cargo clippy --workspace --all-targets --locked -- -D warnings
cargo test --workspace --locked
cargo xtask policy
cargo xtask install-hooks
cargo run --locked -p victory -- config
```

The shell installs its Rust toolchain in the Nix store; it needs no global
rustup installation and does not change your default toolchain. Start your
editor from the shell so it sees these tools. Nix downloads tools on first
entry; shell entry does not install hooks or download the Windows SDK.

### Windows build for Proton

Inside either development shell:

```sh
cargo xwin build --locked --release -p victory --target x86_64-pc-windows-msvc
# target/x86_64-pc-windows-msvc/release/victory.exe

cargo xwin build --locked --profile diag -p victory --features diagnostics \
    --target x86_64-pc-windows-msvc
# target/x86_64-pc-windows-msvc/diag/victory.exe
```

`cargo xwin` downloads the Microsoft CRT and SDK on its first cross-build;
its normal Microsoft licence terms apply. Downloads are cached under
`${XDG_CACHE_HOME:-$HOME/.cache}/cargo-xwin`, or your `XWIN_CACHE_DIR`
override. `XWIN_ARCH` defaults to `x86_64`. The SDK version follows
cargo-xwin's selection; set `XWIN_SDK_VERSION` and `XWIN_CRT_VERSION` when
you need to reproduce a particular SDK/CRT combination.

The shell sets `VICTORY_BUILD_DXC` to its Linux DXC, unless you already set
it. This embeds the indirect-argument clamp and rectangle fallback shaders
in Windows builds. It is distinct from `VICTORY_DXC`, which locates a
Windows `dxcompiler.dll` at runtime.

### Proton environment

```sh
nix develop .#proton                 # adds umu-run and vulkaninfo
# Legacy equivalent:
nix-shell --arg withProton true

vulkaninfo --summary
# Select the MSVC release build produced above:
VICTORY_EXE="${CARGO_TARGET_DIR:-target}/x86_64-pc-windows-msvc/release/victory.exe" \
    ./scripts/victory-proton.sh "/path/to/game/title.exe" --execute

# Select a diagnostics build explicitly:
VICTORY_EXE="${CARGO_TARGET_DIR:-target}/x86_64-pc-windows-msvc/diag/victory.exe" \
    ./scripts/victory-proton.sh "/path/to/game/title.exe" --execute
```

Use the host's Vulkan drivers. On NixOS, enable `hardware.graphics.enable`
and `hardware.graphics.enable32Bit` in the system configuration; NVIDIA
users also need their system NVIDIA driver configured. On other distributions,
install the matching 64-bit and 32-bit Vulkan drivers through the distribution.

UMU manages Proton and the Steam Linux Runtime on first launch. Set
`PROTONPATH` to an installed Proton/GE-Proton directory to choose a version.
See [the launcher guide](proton-launcher.md) for paths and smoke tests.
The Nix shell uses MSVC/cargo-xwin; the separate LLVM-MinGW smoke test needs
the toolchain described in that guide.

To check the shell expressions and synthetic launcher tests, run
`nix flake check`; use `nix fmt flake.nix shell.nix` to format the Nix files.
Update dependencies deliberately with `nix flake update` and commit `flake.lock`.

## Host tests

The workspace has native Linux gates and a Linux CI job. Without Nix, install
the pinned Rust toolchain with rustup and a native C compiler, then run:

```sh
rustup toolchain install
cargo clippy --workspace --all-targets --locked -- -D warnings
cargo test --workspace --locked
cargo xtask policy
bash tests/proton-launcher.sh    # synthetic launcher checks; no Proton needed
cargo xtask install-hooks       # asset-policy check on every commit
```

Tests requiring Windows PE executables or D3D12 are gated to Windows.
Native tests cover the portable code, not Windows GPU execution.

Keep `TMPDIR` outside the checkout. `victory-core`'s policy tests make
temporary folders and expect them to be outside the repository, so with
`TMPDIR` under the checkout `policy::tests::accepts_unrelated_directories`
fails with `InsideRepo`.

To run the Windows test binaries under Wine/Proton, cross-build them with
`cargo xwin test --target x86_64-pc-windows-msvc --no-run` (or the
environment from the next section) and run the `.exe` files under
`target/x86_64-pc-windows-msvc/debug/deps/` with `wine`. Known Wine/vkd3d
gaps can make some of them fail; see the
[launcher guide](proton-launcher.md#testing-without-game-files) for the
`load_probe` fixture override (`VICTORY_HLE_PROBE`).

## Tools on Linux vs running the title

The `victory` subcommands that only read files (`inspect`,
`census`, `lib-exports`, `shader-info`, `translate`, `config`) build as a
native Linux ELF. `translate` reports the validator and pipeline checks as
unavailable off Windows.

`victory run` is different: running the title needs D3D12 and the rest of
the Windows runtime, so it stays the cross-built `victory.exe` under
Proton, as described below.

## Native tool paths

Native Linux tools use the following path rules:

- cache: `$XDG_CACHE_HOME/victory`, else `~/.cache/victory`;
  data: `$XDG_DATA_HOME/victory`, else `~/.local/share/victory`. Empty or
  relative base variables are skipped. A data folder inside the cache is
  refused.
- relative `[paths]` values in `victory.toml` are relative to the file, and
  a leading `~` in them or in the `VICTORY_*` path variables is the home
  directory. A Windows drive path such as the example file's
  `D:\victory-data\game` is refused on Linux instead of being anchored
  next to the file.
- `victory config` prints each path and where it came from (variable,
  file or default).

None of this changes `victory.exe` under Proton: there it is a Windows
program, `LOCALAPPDATA` is the prefix's, and the `Z:` paths below still
apply.

## Cross-building victory.exe without Nix

Needs the pinned toolchain with the `x86_64-pc-windows-msvc` target, LLVM
(`lld-link`, `clang-cl`, `llvm-lib`) and the Windows CRT and SDK from
[xwin](https://github.com/Jake-Shadle/xwin).

```sh
rustup target add x86_64-pc-windows-msvc
xwin --accept-license splat --output ~/.cache/xwin

X=$HOME/.cache/xwin
export CARGO_TARGET_X86_64_PC_WINDOWS_MSVC_LINKER=lld-link
export CARGO_TARGET_X86_64_PC_WINDOWS_MSVC_RUSTFLAGS="-Lnative=$X/crt/lib/x86_64 -Lnative=$X/sdk/lib/um/x86_64 -Lnative=$X/sdk/lib/ucrt/x86_64"
export CC_x86_64_pc_windows_msvc=clang-cl
export CXX_x86_64_pc_windows_msvc=clang-cl
export AR_x86_64_pc_windows_msvc=llvm-lib
export CFLAGS_x86_64_pc_windows_msvc="--target=x86_64-pc-windows-msvc -Wno-unused-command-line-argument -fuse-ld=lld-link /imsvc$X/crt/include /imsvc$X/sdk/include/ucrt /imsvc$X/sdk/include/um /imsvc$X/sdk/include/shared"
export CXXFLAGS_x86_64_pc_windows_msvc="$CFLAGS_x86_64_pc_windows_msvc"

cargo build --release -p victory --target x86_64-pc-windows-msvc
# target/x86_64-pc-windows-msvc/release/victory.exe

cargo build --profile diag -p victory --features diagnostics --target x86_64-pc-windows-msvc
# target/x86_64-pc-windows-msvc/diag/victory.exe
```

The exe imports `VCRUNTIME140.dll`, the UCRT, `d3d12.dll`, `dxgi.dll`,
`d3dcompiler_47.dll` and `xinput1_4.dll`. Proton provides all of them; on a
plain Wine prefix without vcruntime140, run `winetricks vcrun2022`.

## Running under Proton

Tried with UMU-Proton (11.0) via [umu-run](https://github.com/Open-Wine-Components/umu-launcher).
Paths given to `victory.exe` are Windows paths, so use `Z:` plus the Linux
path. The `VICTORY_*` variables override `victory.toml`, as on Windows.

```sh
export WINEPREFIX=$HOME/.local/share/victory/pfx
export GAMEID=umu-victory STORE=none
# PROTONPATH=<Proton dir>           # optional; umu-run uses UMU-Proton when unset

z() { printf 'Z:%s' "${1//\//\\}"; }
export VICTORY_GAME_DIR=$(z "$HOME/victory-data/game")
export VICTORY_DATA_DIR=$(z "$HOME/victory-data/data")
export VICTORY_CACHE_DIR=$(z "$HOME/victory-data/cache")
export VICTORY_LOG=info
# vkd3d-proton writes vkd3d-proton.cache into the working directory by
# default; keep it outside the checkout or `cargo xtask policy` flags it.
export VKD3D_SHADER_CACHE_PATH=$HOME/.local/share/victory/vkd3d-cache
mkdir -p "$VKD3D_SHADER_CACHE_PATH"

# From the repository root: the cargo output from the build step above
# (use .../diag/victory.exe for the diagnostics build).
VICTORY_BIN=$PWD/target/x86_64-pc-windows-msvc/release/victory.exe
# Host logs go outside the checkout, one folder per run.
LOGS=$HOME/.local/share/victory/logs/$(date +%Y%m%d-%H%M%S)
mkdir -p "$LOGS"

umu-run cmd.exe /c "$(z "$VICTORY_BIN") run $VICTORY_GAME_DIR\<the title's exe> --execute > $(z "$LOGS/host.out.log") 2> $(z "$LOGS/host.err.log")"
```

Proton does not pass the Windows console through, hence `cmd.exe /c` with
redirections to keep the log. Those logs can contain title-derived data, so
they live under `$LOGS`, not in the repository. If you copy `victory.exe`
somewhere else, point `VICTORY_BIN` at that copy, also outside the
repository. `crashes.log` is in the data folder as usual.

`VKD3D_SHADER_CACHE_PATH` must be a directory outside the repository. If a
`vkd3d-proton.cache` file ever lands in the checkout, delete it rather than
committing it; `cargo xtask policy` rejects it.

Seen on one machine (NVIDIA RTX 2060 SUPER, UMU-Proton 11.0, release build):
imports bind, the D3D12 device comes up on vkd3d-proton, the first-boot
screens and intro video run at 30 fps, and the title starts loading the
world. Some compute pipelines are refused with `E_INVALIDARG` (NVIDIA has
32-lane waves; see the README's shader row), and the title's view heap is
larger than vkd3d-proton allows on that GPU, so it is capped.

### Indirect draws under Wine

Wine's `D3DCompile` can refuse the shaders that clamp indirect-draw arguments
and expand rectangles. VIctory first tries the system compiler, then uses
build-time DXC bytecode when available, otherwise falls back to runtime DXC.
The Nix cross-build embeds these helpers automatically through
`VICTORY_BUILD_DXC`.

For builds without embedded helpers, supply Windows `dxcompiler.dll` and
`dxil.dll`. `VICTORY_DXC` can point to the compiler DLL or its directory
(use a Windows path under Proton); VIctory also searches beside the shader
validator, beside the executable and in System32.

Wine's builtin `d3dcompiler_47` is usually why the system compiler refuses
first. Its HLSL front end has no `Load` method on an `RWByteAddressBuffer`
(WineHQ bug [60871](https://bugs.winehq.org/show_bug.cgi?id=60871)), and no
`Interlocked` methods until vkd3d got them after the Wine 11.0 release. The
clamp reads its arguments with `Load` and `Load3` and updates the budget with
`InterlockedAdd`, so on Wine 11.0 the first refusal names `Load`:

```
clamp:19:27: E5005: Method 'Load' is not defined on type 'RWByteAddressBuffer'.
```

A build whose clamp also used `InterlockedMax` was refused next, at
`clamp:67:10: E5005: Method 'InterlockedMax' is not defined on type
'RWByteAddressBuffer'.`

Microsoft's compiler accepts the same source. Newer vkd3d has the
`Interlocked` methods but still no `Load` on a byte-address buffer, so a
recent Wine helps only partly. While the clamp does not compile, VIctory logs
`no argument clamp: indirect execution dropped` and drops every indirect draw
and dispatch: the frame counter advances, the picture stays black, and that is
not a rendering bug to chase.

Two ways out, both tried on GE-Proton11-14 (Wine 11.0) with RADV on an RX 9070
XT:

- let the DXC fallback compile it: an embedded helper, or `VICTORY_DXC`
  pointing at `dxcompiler.dll`, or `dxcompiler.dll` beside the exe;
- or copy Microsoft's `d3dcompiler_47.dll` into the run directory and set
  `WINEDLLOVERRIDES=d3dcompiler_47=n,b`, which keeps the builtin as a
  fallback. `WINEDEBUG=+loaddll` shows which one loaded.

## Diagnostics

`VICTORY_D3D12_WARP`, `VICTORY_KEYS`, `VICTORY_STACKS` and the other
variables in the README's Debugging table only work in the `diag` build
above; a release build ignores them. Under Proton, `VICTORY_D3D12_WARP=1`
asks for the WARP adapter, and #41 refuses an adapter that is not a software
one instead of using the real GPU. Add `WINEDEBUG=+seh,+loaddll` for Wine's
view of faults and DLL loads.

### Capture layers

A Vulkan layer enabled for a run changes what that run does, and a crash with
it enabled is not by itself evidence of a VIctory defect (a layer can hide one
as easily as expose one, so check a layer-free run too). With RenderDoc's
capture layer from
Arch's `renderdoc` package in the instance, game runs on this machine ended
1 s to 80 s in with a first-chance `0x80000003` followed by `0xc0000005`
inside `victory-image-*.dll`; a control run of the same exe without the layer
completed 60 s (37.9 fps, `frame=512 draws=3328`). A 60-second control does
not cover faults that happen later, so keep a longer run in mind before
blaming the layer for everything. Keep ordinary runs free of it (no
`ENABLE_VULKAN_RENDERDOC_CAPTURE` in the environment, no `renderdoc` entry in
`VK_INSTANCE_LAYERS` - the loader lets that override the disable filter - or
`VK_LOADER_LAYERS_DISABLE=*renderdoc*`), check
`/etc/vulkan/implicit_layer.d` and `/usr/share/vulkan/implicit_layer.d`, and
confirm what actually loaded (`VK_LOADER_DEBUG=layer` lists it) before
reporting a Wine crash.
